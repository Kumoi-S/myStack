# GPT-6.2 Prompting Guide

> 覆盖：GPT-6.2 Astra、GPT-6.2 Sol
>
> 官方模型指南：Using GPT-6.2

## 1. 模型行为

GPT-6.2 Astra 默认写作风格比前代更简洁、直接。迁移旧 prompt 时，重新检查“be concise”之类的重复要求，避免过度压缩答案。

官方指南指出的重点：
- **Writing**：指定术语、受众、语气和上下文；重点先行。
- **Task completion**：长任务要给模型空间做合理假设并持续推进；说明何时需要用户输入。
- **Coding**：描述仓库约定、复用现有逻辑、兼容性、测试范围和代码可读性要求。
- **Frontend**：如果 UI 有指定视觉方向，明确图片类型、字体、排版和参考样式。

## 2. 长任务与主动性

提示词应明确：
- 要交付的最终结果；
- 哪些工作已经授权；
- 哪些选择必须交给用户；
- 哪些动作不可逆；
- 如何验证完成。

示例：

```text
你负责把本任务推进到可验收的交付状态。
在既定范围内完成必要的检索、修改和验证，不要只给计划。
可以对可逆细节做合理假设，并在结果中标注。
如果存在真正阻塞、需要改变任务范围或涉及不可逆操作，再暂停请求用户决策。
结束前逐项检查验收标准。
```

不要把这段模板当成越权许可；具体执行仍受应用工具权限和用户授权约束。

## 3. Coding Prompt

建议明确：
- 现有代码风格和架构约定；
- 是否优先复用现有逻辑；
- 哪些公开 API / 调用方行为必须保持；
- 改动范围；
- 测试要求；
- 是否允许大规模重构；
- 可读性要求。

示例：

```text
在修改前先检查现有实现和调用方。
优先复用现有类、方法和 API，只在必要时引入新抽象。
保持已有调用方依赖的行为，除非任务明确要求变更。
代码应便于人工审查，不用压缩变量名或一行式技巧替代清晰实现。
运行与本次行为相关的测试，并报告命令和结果。
```

## 4. Frontend Prompt

如果需要指定视觉风格，给出：
- 参考网站/截图；
- 图片风格和内容；
- 字体、字号层级和间距；
- 颜色、布局和组件风格；
- 交互状态；
- 页面文案的目标受众。

不要只写“做得现代、漂亮”。把视觉目标拆成可观察的特征。

## 5. GPT-6.2 API 关键变化

### Reasoning effort

新集成建议从 `medium` 开始。如果旧集成使用 `none` 或 `minimal`，迁移时先评估 `low`。

- Responses API：`reasoning.effort`
- Chat Completions：`reasoning_effort`

### Tool calling

GPT-6.2 Astra / Sol 支持 Chat Completions，但工具调用需要使用 Responses API。

### 不支持的参数

迁移时检查并移除不适用参数：
- Chat Completions：`temperature`、`top_p`、`logprobs`、`top_logprobs`
- Responses：`temperature`、`top_p`、`top_logprobs`，以及相关 logprobs include 配置

### Instructions 与 Prompt Cache

GPT-6.2 开始，Responses API 会把顶层 `instructions` 追加在 `input` 之后。要让稳定指令参与 prompt caching，应把它放在 `input` 数组的第一个 developer message。

将仅在当前请求生效的开发者指令放入顶层 `instructions`。从 GPT-5.5 或更早的型号迁移时，官方指南建议将 `prompt_cache_retention` 改为 `prompt_cache_options.ttl`，并设为 `"30m"`。

稳定指令的示例：

```python
response = client.responses.create(
    model="gpt-6.2-astra",
    input=[
        {"role": "developer", "content": "你是一个严格遵循项目规范的代码审查助手。"},
        {"role": "user", "content": "审查这个 diff，并列出阻断性问题。"}
    ],
    reasoning={"effort": "medium"},
)
```

不要为了更新任务而随意编辑历史前缀。GPT-6.2 的 Responses API 在 prefix edits、部分模型切换和用户/组织变化时会丢弃 reasoning items，可能降低质量并增加重复推理 token。
