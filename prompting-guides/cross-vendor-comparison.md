# Gemini、Claude、GPT 的提示词写法对比

同一个任务，提示词最值得改的地方取决于错误出在哪里。Gemini 的长资料和多模态任务可以先试**标清证据位置与各材料的用途**。Claude 的长任务可以先试**讲清完成责任与何时停手**。GPT-6 系列可以先试**指定交付物的编辑标准，并重新审视旧提示词的详略约束**。下面的句式是从厂商指南推导出的写法，示例用于说明怎样修改提示词，效果应在自己的任务中验证。

## 用同一任务看三种写法

用户请求：“根据旧公告、新公告和后台截图，更新帮助中心的导出说明，核实后交稿。”三份材料分别写着旧入口「报表 → 导出」、新入口「订单 → 导出 CSV」、当前截图上的「下载 CSV」。新公告说仅管理员可导出，截图未显示权限。

三版共享一条业务规则：“截图用于核对当前界面中的可见文字，新公告用于核对权限，旧公告用于识别要替换的旧说明。同一事实出现无法解释的冲突时，在编辑备注中指出。”下面每版只展示最值得试的增量。

### Gemini 4 / 3.8 Flash：给材料分工，问题放在材料之后

```text
[旧公告 A]
[新公告 B]
[当前截图 C]

为帮助中心写一段可直接替换的导出说明。
用 C 核对页面路径与按钮文字，用 B 核对谁可以导出。
如果 C 只显示按钮，权限仍以 B 为准。
正文后附编辑备注，每条只写“事实｜材料编号｜可定位的原文或截图区域”。
```

“结合所有材料”容易让同一句话里的入口、按钮和权限被当成一个事实。把它们拆开以后，模型可以分别选择证据。做视频和文档对照时也一样，可以写“用字幕确认口头承诺，用画面确认实际点击的控件”。如果编号和定位仍然串错，先让模型输出三行事实卡，再让它根据事实卡写稿。短任务可以保留一次交付。 [Gemini 提示词策略](google/01-prompt-design-strategies.md) · [Gemini 4 家族指南](google/03-gemini-4-family.md)

### Claude Fable 5.2 / Opus 5.5：把负责范围和停止条件写在一起

```text
你负责交付这次帮助中心修订的替换稿。可直接重写导出小节，并合并其中重复的步骤。
其他小节保持原有结构。先写完依据充分的部分，再核对入口、按钮和权限。
某一项证据不足时，把该项留在编辑备注里，其余部分继续成稿。
只有缺失信息会改变用户实际操作时，才向编辑提出一个具体问题。
```

Fable 5.2 的指南专门讨论了所有权和谨慎指令。遇到模型只提建议、改完一处就停或频繁问确认时，先检查旧提示词里有没有“全程谨慎”“任何疑问先问”之类的宽泛条款。改成“可以直接改哪些内容”和“什么情况才需要停”。对 Opus 5.5 的长任务，可在续作消息里列出待完成的小节和待核实的事实，再让它从剩余项接着做。 [Fable 5.2](anthropic/02-claude-fable-5.2.md) · [Opus 5.5](anthropic/03-claude-opus-5.5.md)

### GPT-6 / 6.1 / 6.2：指定成稿的编辑方式

```text
直接给出帮助中心的替换段落。读者是正在订单页找导出入口的管理员。
正文按“在哪儿 → 点什么 → 谁能用”展开，用界面原词。
每一步只保留一个动作。只有来源冲突或证据不足会影响发布时，才追加编辑备注。
如果用户已经提供可用原稿，保留与此次变更无关的措辞。
```

现有 GPT-6 系列指南提到早期型号的回答可能较详细、格式较多。迁到 GPT-6.2 Astra 时，先删掉重复的“务必简短”“只给结论”，用读者确实需要的内容约束篇幅。比如“保留入口、权限及例外，省去修改过程”，这样可以防止把实际要用的信息压掉。做局部编辑还可以写“只替换操作步骤，沿用作者的用词”，防止模型顺手重写整段。 [GPT-6](openai/02-gpt-6-family.md) · [GPT-6.1](openai/03-gpt-6.1-notes.md) · [GPT-6.2](openai/04-gpt-6.2.md)

## 按坏输出改写提示词

| 看到的坏输出 | 优先尝试的写法 | 检查改对没有 |
|---|---|---|
| 引用看着齐全，证据其实只支持半句话 | “把可发布的结论拆成独立事实，每项给一处支持它的证据。来源只覆盖部分时，只确认覆盖的部分。” | 用一张有按钮、无权限信息的截图测试，要求按钮和权限分别取证。 |
| “请仔细验证”最后变成一句“已核实” | “交稿前从成稿反查入口、按钮、权限三项。每项标记已确认或待确认，并给出能复查的位置。发现不符先修稿，再核对该项。” | 故意在草稿里放一个旧按钮名，检查它是否被纠正，证据是否真能定位。 |
| 证据冲突时，模型替用户拍板 | “先判断两条材料是否说的是同一版本、同一对象。适用范围不同就分别写。范围相同仍冲突时，把冲突留给编辑，并写清需要核实的那个事实。” | 把截图换成旧版，检查是否能指出到底欠缺当前界面证据还是权限证据。 |
| 问一连串问题，迟迟不给结果 | “能在当前材料上完成的部分先完成。缺失的值可由读者轻松改回时，写明采用的假设。只有答案会改变实际操作时，问一句能决定下一步的问题。” | 缺稿件标题时应仍能起草。缺少会决定操作对象的信息时，应指出要确认的对象。 |
| 好像很友好，读完却不知道点哪里 | “按读者现在看到的页面起笔。每句话一个动作，按钮用原名。仅当失败时有可执行的替代路径，才写下一步。” | 让没看过材料的人找入口。若还得问“从哪页进去”，就补路径。 |
| 每次都生成同样多的小标题 | “常规结果一段话。只有存在两个以上独立动作时才用列表。只有待确认项会影响使用时才加一行说明。” | 短问答与复杂结果分别试一次，确认版式会随信息量变化。 |
| 一处局部需求引发全面重写 | “保留现有结构、术语和作者语气。只改影响本次目标的句子。若满足目标需要改其他段落，在编辑备注里指出原因。” | 同时跑一个只改按钮名的输入和一个确需调整两步顺序的输入。 |
| 态度得体，事实状态却写过头 | “按已经观察到的状态写动词。收到请求写‘已提交’，看到可下载文件才写‘已生成’。仍待确认时，交代用户此刻可以做什么。” | 给出同一任务的处理中、完成、失败三种输入，看措辞是否随状态改变。 |

## 示例怎么选，指令怎么删

- **示例优先展示容易混淆的边界。** 想教模型区分“看见按钮”和“有权点击”，给一对几乎相同的输入。一例有权限说明，另一例只有截图。输出应分别是“仅管理员可导出”和“截图显示导出按钮，权限待确认”。三个都成功的示例很难教会它何时保留未知。 [Claude 提示词最佳实践](anthropic/01-prompting-best-practices.md)
- **要模型模仿风格，就明确模仿哪些成分。** 可以写“参考样稿的句长、用词和操作顺序。页面名称、权限和步骤以本次材料为准”。旧样稿里有过期按钮名时，最好换成中性占位词，避免让格式示例同时充当事实来源。 [Gemini 提示词策略](google/01-prompt-design-strategies.md)
- **用正向动作收紧边界。** 把“别啰嗦、别堆术语、别复述”改成“第一句给结果，下一句给读者要做的动作。后台名词只有在界面可见或影响操作时才出现”。如果模型开始生硬地省略必要条件，给它一个需要保留例外的短示例。 [Claude 提示词最佳实践](anthropic/01-prompting-best-practices.md) · [GPT-6.2](openai/04-gpt-6.2.md)
- **把写法冲突改成优先顺序。** “保持原文风格、全文现代化、尽量少改”容易互相拉扯。写成“本次只修出错的步骤。改到的句子沿用原文称呼和语气。读者完成操作所需的路径与限制必须保留”。 [GPT-6](openai/02-gpt-6-family.md)
- **对可判断的工作拆步，对简单交付删步骤。** 检索证据和润色经常串台时，先产出可核对的事实卡，再生成成稿。短任务可以只给交付标准和一项关键核对。长模板里的逐步工作流程应当对应实际发生过的错误。 [Gemini 提示词策略](google/01-prompt-design-strategies.md) · [OpenAI 推理提示词与评测](openai/05-reasoning-tools-and-evals.md)

改一条就用原来的坏例和一个普通例各跑一次。比如新增“冲突时留编辑备注”之后，既要检查冲突例能否留下足够信息，也要检查三份材料一致时是否仍能直接交稿。比较时看证据是否支持结论、读者能否完成操作、模型是否额外改变了原文。
