# Gemini Prompt Design Strategies

> 类型：通用 Prompting Guide
>
> 适用：Gemini API；复杂场景需结合具体模型指南和 API 参数文档。

## 1. 先把任务说清楚

高质量提示词应让模型知道：
- **目标**：要完成什么，而不是只描述主题。
- **输入**：哪些文本、文件、图像或数据是依据。
- **约束**：范围、时间、长度、语气、禁止事项和资源限制。
- **成功标准**：什么结果算完成。
- **输出**：JSON、Markdown、表格、代码或其他结构。

避免含糊的词，例如“详细一点”“更好”“专业”。把它们转成可检查的标准，例如“列出 5 个风险，每项包含概率、影响和缓解措施”。

## 2. 用一致的结构组织提示词

对于复杂任务，可以使用 Markdown 标题或 XML 标签把不同部分隔开。每个 prompt 内尽量保持同一套结构，不要同时混用多套含义不清的标记。

```xml
<role>
你是负责审查 Python 服务的资深工程师。
</role>

<context>
<repository>
[代码、目录结构、运行环境]
</repository>
<requirements>
[业务需求与现有约束]
</requirements>
</context>

<task>
审查并修复指定模块中的并发问题。
</task>

<constraints>
- 保持公开 API 兼容。
- 先复现问题，再修改。
- 不要修改无关模块。
</constraints>

<output_format>
列出根因、改动文件、测试结果和未解决风险。
</output_format>
```

## 3. 角色、约束和输出要求

- 角色说明模型应采用的专业视角、责任和表达风格。
- 约束应写成明确的“必须/不得/仅在……时”。
- 如果有术语或参数可能产生歧义，给出定义。
- Gemini 3 系列默认回答较直接；需要更长、更口语或更完整的内容时，显式说明篇幅和细节级别。
- 需要稳定行为时，把长期规则放进 `system_instruction`，不要只在某次用户输入里临时提及。

## 4. 示例（Few-shot）

示例能展示格式、边界和判断标准。示例应：
- 与真实任务接近；
- 覆盖正常输入、边界输入和异常输入；
- 输入和输出严格一致；
- 避免让模型学到不想要的偶然格式。

如果任务很简单，先尝试 zero-shot；只有当模型对格式或边界的理解不稳定时再增加示例。

## 5. 把复杂任务拆成组件

可选策略：
1. **拆分指令**：将一个过长 prompt 拆成独立步骤。
2. **串联 prompt**：上一步输出成为下一步输入，适用于检索→分析→写作。
3. **并行处理**：不同数据块分别处理，再汇总。
4. **先抽取后生成**：先抽取事实或字段，再根据抽取结果生成最终内容。

每一步都应定义输入、输出 schema 和验证方式，防止错误在链路中放大。

## 6. 长上下文

- 把大段参考资料先放入上下文。
- 在资料和问题之间加过渡语，例如“根据以上材料……”。
- 在末尾明确提出具体问题和输出要求。
- 多个文件分别标注来源、编号和用途。
- 对长资料要求引用原文位置，避免模型把外部知识和资料事实混在一起。

## 7. 多模态输入

图像、音频、视频和文本可以共同作为输入。提示词要明确说明每种模态的作用，例如：
- “根据图像读取表格数值，使用文字说明中的定义计算结果。”
- “只转写音频中的发言，不要根据背景画面补充内容。”
- “按时间顺序总结视频中的动作，并标注时间戳。”

不要只写“分析这个文件”；应说明要识别什么、忽略什么、输出什么。

## 8. 推理

Gemini thinking 模型会在回答前进行内部推理。复杂问题可提高 `thinking_level`，通常不需要要求模型把内部推理逐字输出。若需要可审计结果，应要求提供结论、关键依据、假设、计算步骤或可验证证据，而不是要求披露私有思维链。

## 9. 参数与评测

Prompt 和生成参数需要一起评估：
- `thinking_level`：主要控制推理深度、延迟和 token 消耗。
- `max_output_tokens`：输出硬上限；thinking token 也可能计入预算。
- 结构化输出：复杂 JSON 应优先使用 API schema，而不是仅在自然语言中要求“返回 JSON”。

建立固定测试集，至少记录任务成功率、结构合法率、幻觉/遗漏率、延迟和成本。
