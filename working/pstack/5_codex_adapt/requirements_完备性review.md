# 完备性审查

核对当前 `cursor-codex.md`、[编写要求](requirements_plan.md)、[Stage 4 底稿](../4_codex_openai_yaml/output/)和[上游适配器](../../../sources/cursor-plugins/harness/pstack/claude-code/docs/harness/claude-code.md)。

1. 双向核对。逐条映射追到实际使用处，再从底稿的 agent、skill、playbook 和脚本反查遗漏。核对表外全局要求、重复项、已由前序阶段处理的项及与原行为冲突的项。覆盖结论写明查过的范围和依据。漏项指出具体文件、行和补入位置。
2. 按实际调用核对 Codex 的工具、字段、参数、路径、命令及默认行为，引用可复查的工具定义、命令帮助或实现。实际存在能力缺口时，核实处理办法能否达成原目的；若仍有缺口，指出具体步骤。
3. 提返修前，说清哪个调用按当前映射会遗漏、做错或做不到。先从底稿证明该行为确有需要，再查工具是否支持。稿中已有的回退命令不能单独作为补写其等待、续接或失败处理的依据。当前工具能完成的调用直接核验。假设工具将来不可用、换环境或增加权限限制，不构成补写理由。

按主代理给的稿本、轮次和共享目录独立完成本项审查。只写本轮分配给自己的 Markdown 文件，交回其路径。结尾写明已查范围及结论（通过／有意见）；即使另一项已报问题也要查完。本轮稿件正文和状态由编写者、主代理分别维护。

按表格顺序记录意见。一条意见用一个标题，写稳定编号（首次用 C 前缀）、章节和左列原文（表外写段首，遗漏写补入位置）；正文引用证据，说明影响和最小改法。后续同一问题引用原编号，保留原话。澄清时按主代理指出的疑点在共享目录另交答复。

返修后复查时沿用上一轮已核实的结论。按编号检查改动及受影响的对应项，交代每项是否解决，并补记改动实际引入的问题。
